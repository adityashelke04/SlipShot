# Drag transfer source review

**Historical review:** the accepted-only lifetime and 32-file policy below were superseded in 0.2.9. Native regression testing found that a target can consume the file path while returning None; deleting that file breaks delayed reads. See the [2026-11-01 RCA](DRAG_DROP_RCA.md) for the fix and current verification evidence.

Review date: 2026-10-30. Scope: `Services/DragTransfer.cs`, `Core/PreviewGesture.cs`, `UI/PreviewWindow.cs`, and the new `AppController` integration. The connected image writer, renderer, preview lifetime, resource policy, shutdown entry point, and test bodies were also read. This was a read-only source audit; the reviewer ran no build, tests, GUI, native drag, clipboard operation, or desktop capture.

**What this change does:** An explicit drag from the preview prepares flattened image data in file, bitmap, and PNG formats. An accepted copy leaves its temporary file available for later reads; a cancelled or interrupted operation attempts to remove its own file. The preview separates click-to-edit from dragging and keeps its lifetime stable while Windows runs the drag operation.

**No blocking source defect was found in the final reviewed version.** Two integration concerns raised during review were resolved before this verdict: the preview now defers closure while a drag is active, and startup/preview text now discloses that dragging writes a temporary PNG.

## Checked paths

| Concern | Source conclusion | Evidence |
| --- | --- | --- |
| Copy versus cancellation | The production caller allows `DragDropEffects.Copy` and treats a returned Copy flag as acceptance. None, another non-Copy result, or an exception leaves the lease on its cancellation path. It does not claim that a returned Copy proves a target saved or uploaded the image successfully. | `AppController.cs:145`; `DragTransfer.cs:143`. Microsoft documents the returned effect as the target's final effect, rather than a general guarantee about later processing: [WPF DoDragDrop](https://learn.microsoft.com/en-us/dotnet/api/system.windows.dragdrop.dodragdrop). |
| Late file reads | Accepted completion removes the path from the active set and refreshes its timestamp. Later `Dispose` calls are no-ops. Shutdown does not delete accepted transfer files, so a target that already received the path can open it after the drag returns or the source app exits, until later cleanup or an external change removes it. | `DragTransfer.cs:79`, `DragTransfer.cs:143`; `AppController.cs:244`. |
| Late PNG reads | Accepted completion deliberately leaves the managed PNG stream readable. Its lifetime follows references to the data object; it is not kept in an unbounded application list. This supports late reads while that data object and source process remain available. It does not promise stream delivery after the source process exits. | `DragTransfer.cs:37`, `DragTransfer.cs:143`. |
| Export contents | The controller renders an `EditDocument` before preparing the transfer. The file writer renders only supplied pixels, excludes inherited metadata/thumbnails, verifies the encoded dimensions, and uses a non-overwriting rename. The transfer's bitmap is decoded from that same PNG, so advertised formats share the encoded image. | `AppController.cs:148`; `Core/DocumentRenderer.cs:13`; `Services/ImageFiles.cs:12`; `DragTransfer.cs:34`. |
| Cleanup ownership | Sweep visits only the top-level drag folder, accepts only the exact prefix + GUID + `.png` name form, skips reparse-point files, and does not expire this store's active leases. Deletion rechecks the parent path and filename. Directory ancestry is checked for redirection before writes and deletion. No recursive delete is used. | `DragTransfer.cs:57`, `DragTransfer.cs:97`, `DragTransfer.cs:109`, `DragTransfer.cs:117`. |
| Store budget | Recent accepted transfers are not evicted to admit another drag. The store rejects another transfer when the retained count reaches 32 or retained bytes reach 256 MiB, and removes a newly encoded candidate that would exceed the remaining byte budget. | `DragTransfer.cs:12`, `DragTransfer.cs:27`, `DragTransfer.cs:36`. |
| Gesture threshold | Movement smaller than both system thresholds remains a click candidate. Reaching either threshold starts one drag; another move cannot start a second drag from the same press. Release after a drag is not a click. Cancellation clears both states. | `Core/PreviewGesture.cs:5`; `PreviewWindow.cs:124`. |
| Accidental click after drag | The thumbnail handles its mouse-down and mouse-up events rather than letting the Button's default mouse click path compete with the gesture. A plain release edits only inside the thumbnail. The separate Click handler retains keyboard activation. The drag `finally` clears the gesture, preventing the later release from opening an editor. | `PreviewWindow.cs:124`, `PreviewWindow.cs:157`, `PreviewWindow.cs:167`. |
| Mouse capture loss | The window sets its independent `dragging` flag before releasing mouse capture. `LostMouseCapture` therefore cannot clear the active drag state. Lost capture outside a drag cancels the click candidate. | `PreviewWindow.cs:142`, `PreviewWindow.cs:175`. |
| Expiry while held or dragged | Timer advances pause for both a held gesture and an active drag, including movement outside the thumbnail. On return, the preview gets a fresh lifetime and stopwatch baseline. This also prevents time spent inside the native call from causing an immediate expiry afterward. | `PreviewWindow.cs:157`, `PreviewWindow.cs:219`. |
| Nested close/display change | Dismiss and Closing set a pending close while dragging. Closing is cancelled at that point, keeping the controller's preview reference and active-drag guard intact. `QueryContinueDrag` requests cancellation when closure is pending; the final close occurs after the drag callback returns. A display-change handler can clear the queue during this interval without creating a replacement preview. | `PreviewWindow.cs:177`, `PreviewWindow.cs:226`, `PreviewWindow.cs:240`; `AppController.cs:131`, `AppController.cs:227`. |
| New capture, reopen, forget, and tray exit | These controller operations check `preview.IsDragging` before hiding/replacing/closing the preview. They cannot enter their destructive preview paths while the active drag flag remains set. Tray exit asks the user to finish or cancel the drag. | `AppController.cs:71`, `AppController.cs:136`, `AppController.cs:143`, `AppController.cs:215`. |
| Failure recovery | Expected preparation/native errors become an inline unavailable message with the detailed error in the tooltip. The lease scope cleans a nonaccepted transfer, and the preview `finally` clears gesture state and resets the timer. The message after a normal return says the image is ready to drag again, not that a drop necessarily succeeded. | `PreviewWindow.cs:145`; `AppController.cs:148`; `DragTransfer.cs:49`. |

Windows enters its own drag loop and calls source/target callbacks while a drag is in progress; this is why close and reentry guards were traced across the caller and window. [Microsoft OLE DoDragDrop documentation](https://learn.microsoft.com/en-us/windows/win32/api/ole2/nf-ole2-dodragdrop) was checked on 2026-10-30. The source review is not an observation of Windows event ordering on this machine.

## Test bodies examined

`DragTransferTests.cs` checks construction without writes; matching flattened pixels and absent source metadata/thumbnail in all three formats; accepted file and PNG availability after disposal; cancellation and unrelated-file preservation; exact-name/top-level/active-lease sweep boundaries; count and byte rejection; and unwritable destinations. `PreviewGestureTests.cs` checks threshold/single-drag behavior, cancellation, and lifetime pause outside bounds. Existing lifetime/resource tests and the application shutdown entry point were also read.

These tests exercise managed policy and filesystem behavior. They do not cover the actual `DoDragDrop` call, routed mouse/keyboard events, COM data marshaling, a target that reads later, display changes inside the drag loop, or operating-system shutdown. The coordinating agent owns execution results; this review does not independently claim that tests passed.

## Deliberate limits and verification still needed

- **Expiry is opportunistic.** Twenty-four hours makes an accepted file eligible for cleanup during a later `Prepare`; it is not a deletion deadline. If no later drag occurs, the file may remain indefinitely. The final preview tooltip states this. Memory-forget does not promise to remove transfer files.
- **The disk budget is a retained-store limit.** A candidate PNG is fully encoded before its size is checked. Temporary encoding bytes can briefly exceed the retained 256-MiB budget. The image resource policy is likewise a buffer estimate, not a measured process-memory guarantee.
- **Cleanup can fail.** Locked files and denied access are caught to preserve application recovery. A cancelled transfer may remain until a later successful sweep. This is not a secure-erasure guarantee.
- **External applications remain unverified.** Test at least one filesystem target and one image/file-accepting application, including Copy, Escape/None, rejection, a delayed file open, and a delayed PNG request. Inspect the resulting pixels and confirm one drop does not open the editor.
- **Native event interactions remain unverified.** Check held-button expiry, dragging outside the preview, keyboard edit activation, capture/reopen/forget/exit commands during the drag, and a display-change close request. Normal tray shutdown is source-guarded; forced process termination or OS session shutdown cannot be certified by this review.

No code edits, extra abstractions, or dependency additions are requested by this audit. Keep native checks explicitly unrun until they are permitted and actually performed.

**Verdict: source review passes; native drag interoperability is not established.**

**Not checked:** build/test execution, live desktop input, real target interoperability, process memory, and OS shutdown behavior.
